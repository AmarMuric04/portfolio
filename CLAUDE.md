# CLAUDE.md

Guidance for working in this repository. Follow it exactly — the goal is code that is clean, consistent, and unmistakably intentional. When something here is ambiguous, match the surrounding code before inventing a new pattern.

## Project

Personal portfolio site. Single-page React app that showcases projects, education, and experience.

- **Build tool:** Vite 6 (`type: module`)
- **Framework:** React 18 + TypeScript (strict via `tsc -b`)
- **Routing:** TanStack Router — file-based, via `@tanstack/router-plugin/vite`
- **Styling:** Tailwind CSS v4 (via `@tailwindcss/vite`) — no config file, no separate PostCSS setup
- **Animation:** `framer-motion`
- **Icons:** local SVG components in `src/assets/svgs.tsx` and `lucide-react`

## Commands

```bash
npm run dev      # start Vite dev server
npm run build    # tsc -b && vite build — MUST pass with zero TS errors
npm run lint     # eslint . — MUST pass clean
npm run preview  # preview the production build
```

Before considering any change done: `npm run build` and `npm run lint` both pass with zero errors and zero warnings.

## Directory layout

```
src/
  assets/       static data (projects, education, techs) + SVG components
  components/   UI, organized by atomic design (atoms/, molecules/, organisms/)
    ui/         shadcn/ui primitives (CLI-generated; flat, do not restructure)
  hooks/        reusable hooks (useIntersectionObserver, useAnimateNumber)
  pages/        route-level screen components (rendered by a route file)
  routes/       file-based route definitions (thin — see Routing below)
  routeTree.gen.ts  AUTO-GENERATED by the router plugin — never edit, kept in VCS
  types.ts      the single megafile for all shared TypeScript types
  utils/        pure helpers (cw, ...)
  router.tsx    createRouter(routeTree) + the typed Register augmentation
  index.css     Tailwind import + theme tokens + keyframes
```

Keep new files in the folder that matches their role. A new UI element goes in the correct atomic level under `components/` (see below), a static content shape goes in `assets/`, a shared type goes in `types.ts`.

## Structure conventions

These four rules govern how code is physically laid out. They are not optional — a change that ignores them is not done.

### 1. A folder per thing

Every component lives in **its own folder**, not as a loose `.tsx` file next to its siblings. The folder is named after the component and contains the component file (plus anything that belongs only to it — a sub-component, a local hook, a `.module`-style concern). Barrel the folder with an `index.ts` re-export so imports stay clean:

```
components/atoms/ActionButton/
  ActionButton.tsx     # the component
  index.ts             # export { default } from "./ActionButton"
```

Import from the folder (`components/atoms/ActionButton`), never from the inner file path.

### 2. Split things up

Prefer many small, focused units over few large ones. A component that renders several distinct sections should be broken into child components; a handler that does two unrelated things should be two handlers. If a file is getting long or a component is juggling more than one responsibility, split it before adding to it. Small pieces that each do one thing are the default — large multi-purpose files are the exception you must justify.

### 3. One type megafile

**All** shared TypeScript types live in a single `src/types.ts`. Do not scatter types across per-feature files, and do not declare a shared shape inline in a component. Add new types to `types.ts` and import them from there. Types that are truly local to one component (a props interface) stay in that component's file — everything shared goes in the megafile.

### 4. Atomic component folders

`components/` follows atomic design. Every component belongs to exactly one level:

- **`atoms/`** — smallest reusable primitives with no dependency on other components (`ActionButton`, `StatusButton`, `ProgressBar`, an icon wrapper).
- **`molecules/`** — small compositions of atoms that form one unit (`NavBarItem`, `Skill`, `ProjectTech`, a labeled control).
- **`organisms/`** — larger self-contained sections composed of molecules and atoms (`Header`, `Project`, `Modal`, `EducationList`).

Route-level screens stay in `pages/`, not `components/`. When you add a component, decide its level first, then create its folder (convention 1) at that level. When unsure between two levels, pick the lower one that still fits.

## Routing — TanStack Router, file-based

Routing is **file-based**. The `@tanstack/router-plugin/vite` plugin watches `src/routes/` and regenerates `src/routeTree.gen.ts` on every dev/build.

- **One file per route** under `src/routes/`. Each is thin: it declares the route with `createFileRoute("/path")({ component })` (or `createRootRoute` for `__root.tsx`) and delegates rendering to a screen in `pages/`. Route files hold routing concerns (path, loaders, guards) — never page markup.
- `__root.tsx` is the app shell: its `component` is the layout (theme wrapper + `Header` + `<Outlet />`) and its `notFoundComponent` handles unmatched paths.
- `src/routeTree.gen.ts` is **generated** — never hand-edit it, and it stays committed so `tsc -b` (which runs before Vite) always resolves it.
- The router is created once in `router.tsx` (`createRouter({ routeTree, defaultPreload: "intent" })`) with the `declare module "@tanstack/react-router" { interface Register }` augmentation so links are type-checked.
- Navigate with `Link` from `@tanstack/react-router`; read the active path with `useRouterState({ select: (s) => s.location.pathname })`. Do not reach for `react-router-dom` — it has been removed.

## Styling — this is the heart of the project

### Tailwind only

All styling is done with Tailwind utility classes in `className`. Do **not** write inline `style={{ ... }}` objects and do **not** add new CSS classes to `index.css` unless it is a genuinely global concern (a theme token, a keyframe, or a `::selection`-style rule that Tailwind cannot express).

### The theme system is the single source of truth for color

Colors are **never** hardcoded per-component. `index.css` defines CSS variables under `:root` (light) and `[data-theme="dark"]`, exposed as `theme-*` utility classes:

- `theme-background`, `theme-surface`, `theme-surface-alt` — backgrounds
- `theme-title-text`, `theme-text-primary`, `theme-text-secondary`, `theme-container-text` — text
- `theme-accent`, `theme-secondary-background`, `theme-border` — accents and borders

**Always reach for a `theme-*` class before a literal Tailwind color.** A raw `text-black`, `bg-[#123456]`, or `border-gray-700` in a component is a bug — it breaks the light/dark unity. If you need a color the theme does not offer, add a token to **both** `:root` and `[data-theme="dark"]` in `index.css`, expose it as a `theme-*` class, then use that class. This keeps the design unified across every surface.

Pair color transitions with `transition-all` so theme switching animates smoothly, exactly as existing components do.

### Conditional classes: use `cw`, never `${}`

Do **not** build class strings with template-literal interpolation. This pattern is banned:

```tsx
// ❌ banned — hard to read, easy to leave stray whitespace
className={`transition-all ${isOpen ? "rotate-180" : ""} pr-12`}
```

Use a `cw` (class-when) helper for all conditional composition:

```tsx
// ✅ required
className={cw("transition-all pr-12", isOpen && "rotate-180")}
```

`cw` takes any number of arguments, drops falsy ones, and joins the rest with a single space. If it does not yet exist, create it once at `src/utils/cw.ts` and import it everywhere conditional classes are needed. Static class strings that have no condition stay as plain string literals — do not wrap those in `cw`.

When you touch a component that still uses `${}` for classes, convert it to `cw` as part of the change.

## Component libraries — don't reinvent, compose

Do **not** hand-roll UI primitives. If shadcn/ui (or a library it wraps) provides it, use that — buttons, dialogs, dropdowns, tabs, tooltips, popovers, inputs, sheets, accordions, toasts, and so on.

### shadcn/ui everywhere

- Every UI primitive comes from **shadcn/ui**. Add a component with the CLI (`npx shadcn@latest add <name>`); it lands in `components/ui/` — do not edit those generated files except to apply the theme (see below).
- Building a bespoke `<button>`, `<dialog>`, dropdown, or overlay from scratch is banned. If you catch yourself writing raw interactive markup that shadcn already offers, stop and pull in the shadcn component.
- Compose shadcn primitives into our atoms/molecules/organisms rather than styling raw elements. Our own components are thin, theme-aware compositions over shadcn — never reimplementations.
- shadcn components must still obey the theme system: colors flow through the `theme-*` classes / CSS variables, not shadcn's default palette. Wire the theme tokens into the shadcn component instead of hardcoding colors.
- `components/ui/` (shadcn) is exempt from the atomic-folder and folder-per-thing rules — it keeps shadcn's own flat layout so the CLI can update it. Everything else follows the structure conventions.

### Modals: `@ebay/nice-modal-react`, always

**All** modals/dialogs use **`@ebay/nice-modal-react`** for their state and lifecycle. Do not manage modal open/close with local `useState`, arrays of open ids, or hand-written overlays — that pattern (as in the legacy `Modal.tsx`) is being replaced.

- Register each modal with `NiceModal.create(...)`, render the shadcn `Dialog` inside it, and open it imperatively with `NiceModal.show(TheModal, props)`.
- Never pass `open`/`setIsOpen` props around to drive a modal. Nice-modal owns that; components just call `show`/`hide`/`remove`.
- Wrap the app once in `<NiceModal.Provider>` (in `main.tsx` / `Root`).
- The visual dialog is shadcn's `Dialog`; nice-modal only orchestrates it. shadcn for the UI, nice-modal for the state — every time.

When you touch a component that still manages a modal with local state, migrate it to nice-modal + shadcn `Dialog` as part of the change.

## Component conventions

- Function components typed as `React.FC<XProps>`, with a named `interface XProps` declared directly above.
- One component per file; `export default` at the bottom.
- Props destructured in the signature; give optional props sensible defaults there (`classes = ""`).
- `useState` calls carry explicit type parameters (`useState<boolean>(false)`).
- Strings use double quotes; statements end with semicolons; two-space indentation.
- Keep JSX readable — one logical block per line, and let Prettier-style wrapping happen naturally rather than cramming attributes.

## Functions — no throwaway one-liners

Do **not** introduce one-line helper functions. If a piece of logic is trivial enough to be a single expression, inline it at the call site. If it is worth extracting, it earns a real, multi-statement function with a descriptive name — the kind that lives in `src/utils/` (`filterProjects`, `getAge`) or in a focused hook (`useProjectFilters`'s `cycleRecord`). A named function should do enough to justify its name; a one-liner wrapper just adds indirection.

This applies to event handlers and derived-value helpers alike: either inline the trivial case or write a substantive, well-named function — never something in between.

## Readability — breathe

Code should have room to breathe. Separate distinct concerns with blank lines so intent is visible at a glance:

- Blank line between logical groups of `useState`/hook declarations and the effects/handlers that follow.
- Blank line between each handler or helper function.
- Blank lines between sibling JSX blocks that represent different sections of the UI (header block, body block, footer block) — mirror the spacing already in `Project.tsx`.
- Never pack unrelated statements together just to save vertical space.

Unified and nicely separated beats dense. Prefer clarity over compactness every time.

## TypeScript

- All shared types live in the single `src/types.ts` megafile; do not redeclare a shape that already exists there and do not create per-feature type files.
- A component's own props interface stays in that component's file — only shared shapes go in the megafile.
- Type props, state, and function parameters explicitly. Avoid `any`.
- Static content (projects, techs, education) is typed data in `src/assets/`, keyed and consumed by components — add new content there, not as hardcoded JSX.

## Definition of done

A change is complete only when:

1. `npm run build` passes (zero TS errors).
2. `npm run lint` passes (zero warnings).
3. All colors go through `theme-*` classes and render correctly in **both** light and dark themes.
4. Conditional classes use `cw`, not `${}`.
5. No one-line helper functions were added.
6. Every new component lives in its own folder at the correct atomic level, split into focused pieces.
7. Shared types were added to `src/types.ts`, not a new per-feature file.
8. UI primitives come from shadcn/ui — nothing hand-rolled that shadcn already provides.
9. Every modal uses `@ebay/nice-modal-react` for state and a shadcn `Dialog` for the UI — no local open/close state.
10. The diff reads cleanly — blank lines separate logical sections, and the styling stays consistent with the rest of the app.
